# Journal des décisions (ADR léger)

Chaque décision métier verrouillée est consignée ici. Format : identifiant, date, décision, raison. Une décision n'est « réelle » qu'une fois écrite ici et commitée. Une décision qui en annule une autre le dit explicitement.

| D-017 | Grand livre BV : toute opération de solde (crédit/débit) s'exécute dans une transaction DB avec verrouillage de la ligne du membre (SELECT ... FOR UPDATE), pour garantir l'invariant « solde jamais négatif » sous concurrence. Mouvements en montant signé + balanceAfter stocké. Le solde du membre est la seule source de vérité, le grand livre en est le journal auditable. | Fondation financière ; sécurité des soldes. |
| D-017b | RBAC des endpoints BV : génération (genesis, création de valeur ex nihilo) = SUPER_ADMIN uniquement ; ajustement manuel = SUPER_ADMIN + MANAGER (motif obligatoire, tracé AuditLog) ; consultation solde/historique = les 3 rôles. Tests séparés : `npm test` (unitaire, sans DB) vs `npm run test:int` (Postgres docker, dont le test de concurrence). | Sécurité : l'action la plus sensible (créer du BV) est la plus restreinte. |
| D-018 | Révise D-011 (« pas de KYC »). Vérification d'identité légère et NON bloquante : à l'inscription, le membre choisit un type de pièce (CIN / permis / passeport) et joint une image. Statut (PENDING/VERIFIED/REJECTED) + badge « vérifié » apposé par l'admin. N'empêche jamais l'activité du membre ; informe l'admin, qui peut ensuite bloquer ou demander correction. Champs/upload : Tranche 4 (stockage fichier local pour ce scope, sécurisation approfondie plus tard). File de tâches admin + action de vérification : Tranche 8. | Consigne cliente. |
| D-019 | Réseau amorcé par 7 comptes de seed ACTIFS sur 3 niveaux : racine NP000963 ; niveau 2 NP000964 (gauche) / NP000965 (droite) ; niveau 3 NP000966-967 sous NP000964, NP000968-969 sous NP000965. Le compteur auto-incrément des codes membres reprend après NP000969. Le compte racine n'est pas l'admin. | Consigne cliente (données d'amorçage). |
| D-020 | **Tranche l'ambiguïté §5.2 / §5.4.** À l'activation, le palier est crédité sur la jambe concernée de **TOUS** les uplines jusqu'à la racine, quel que soit leur état (INSCRIT, ACTIF, INACTIF). Le filtre « actif » ne dit pas *qui est crédité* mais *qui est rémunéré* : le run hebdomadaire ignore les non-ACTIFS. Sans cela, un INSCRIT n'aurait jamais de points sur ses jambes, sa baseline vaudrait toujours 0 et la mécanique de baseline (§5.3, §5.8, D-013) serait sans objet. | Cohérence de la baseline ; §5.2 « chacun de ses uplines successifs, jusqu'à la racine ». |
| D-021 | L'inscription est un endpoint **public anonyme** (code sponsor + code upline + jambe saisis au formulaire), protégé par rate-limiting. Le nouvel affilié choisit son mot de passe. Renforcement futur possible (OTP e-mail/SMS), qui réviserait D-011. *(Confirme et remplace le brouillon « D-020 = inscription publique, à valider ».)* | Consigne cliente. |
| D-022 | L'**upline de placement doit appartenir au sous-arbre du sponsor** (ou être le sponsor lui-même). Vérifié à l'inscription par CTE descendante. | Empêche de placer un filleul n'importe où dans l'arbre global (positions définitives d'un tiers saturées, jambes gonflées artificiellement). |
| D-023 | **Aucune route HTTP d'activation.** L'activation est un service interne (seed, tests, puis checkout e-card en Tranche 5/6). Une route admin créerait un chemin d'activation sans e-card, que §5.3 et §7.1.4 interdisent. | Périmètre : la seule porte d'entrée en ACTIF reste l'achat par e-card finalisé. |
| D-024 | **Verrouillage (technique).** Toute transaction touchant plusieurs lignes `Member` les verrouille par **`id` croissant**, en une seule instruction, avec **`FOR NO KEY UPDATE`** (jamais `FOR UPDATE` : il entre en conflit avec le `FOR KEY SHARE` que prend tout INSERT référençant le membre — login, e-card, inscription d'un filleul — et provoque blocages et interblocages). En joignant une CTE, verrouiller la table de base (`OF m`), jamais la CTE. Voir `.claude/rules/tree.md`. | Bug de concurrence reproduit sur PostgreSQL 16 en Tranche 4 ; corrige rétroactivement le grand livre BV (D-017). |
